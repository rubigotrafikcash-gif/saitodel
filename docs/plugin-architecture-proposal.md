**Статус: DRAFT / на согласование. Дата: 8 ноября 2026 года.**
Задача: [#1 — установить регламент и развить плагин](https://github.com/rubigotrafikcash-gif/saitodel/issues/1).
Основа: согласованный регламент v1.0 и исходники в коммите `674d9f9365acf1a434167d69ebdd486653cbc311`.
Этот документ описывает следующее обновление. Он не подтверждает установку, выпуск плагина или проведение пилота.

## 1. Рекомендуемое устройство

Один плагин, один входной навык `saitodel`, единый источник правил в текущем репозитории.
Координатор ведёт задачу, исполнитель создаёт результат, отдельный проверяющий оценивает его по исходным требованиям.
Work и Codex получают одинаковые правила; запуск агентов и проверки зависят от реально доступных средств среды.
Для первой версии предлагается пакет с инструкциями и шаблоном задания. Отдельный сервис для этого не требуется.

| Область | Решение проекта | Основание |
| --- | --- | --- |
| Правила | Существующие SKILL.md и references остаются каноническими | Уже согласовано |
| Роли | Координатор, исполнитель, независимый проверяющий | Уже согласовано |
| Поставка | Один навык внутри плагина; без обязательных MCP, hooks и runtime | Новое предложение |
| Передача контекста | Один дополнительный orchestration.md и один шаблон записи запуска | Новое предложение |
| Конфигурация Codex | Штатное делегирование без обязательных custom agent TOML | Новое предложение |
| Стек сайта | Существующий стек, мобильная адаптация, 3D только по задаче | Уже согласовано |
| Инженерные проверки | Доступный «Мой вайбкодер», соразмерно изменению | Уже согласовано |
| Русский текст | Доступный «Словодел», с сохранением подтверждённых фактов | Уже согласовано |

Преимущество предлагаемого варианта — минимум компонентов для установки и сопровождения.
Он использует существующие подключения и не требует новых API-токенов или серверов.
Делегирование расходует ресурсы модели; экономию токенов или ускорение можно оценить только по выполненному пилоту.

## 2. Утверждённые границы

- Сохраняются бриф, аудитория, смысл, CTA, концепции, адаптив и проверка результата.
- Для пилота одновременно активны не более трёх агентов, включая координатора.
- Предусмотрены первичная проверка и до двух циклов «исправление → повторная проверка».
- Если обязательные критерии остались невыполненными, результат — `BLOCKED`.
- За каждым изменяемым файлом закреплён один исполнитель; пользовательские правки сохраняются.
- Статусы сборки, визуального просмотра, сценариев и публикации ведутся независимо.
- Роль проверяющего не создаёт отдельного Linux-пользователя, прав или изоляции.
- Специалисты и внешние источники подключаются выборочно; заимствования требуют проверки версии и лицензии.
- Первый сравнительный пилот — сайт Натальи после фиксации входов и критериев.

Эти решения повторно согласовывать не требуется. На согласование выносится только новая упаковка и перечисленные выше дополнения.

## 3. Источник и состав будущего пакета

Текущие восемь файлов навыка остаются на своих местах в репозитории.
При подготовке релиза они копируются в пакет из выбранного коммита; пакет не становится второй редактируемой основой.
Новые orchestration.md и шаблон добавляются в source только после согласования этого проекта.

| Путь в будущем пакете | Откуда берётся и что содержит |
| --- | --- |
| plugin.json | Manifest существующего плагина после установления его идентичности; сохраняются ID и представление |
| skills/saitodel/SKILL.md | Канонический SKILL.md; краткий вход и ссылки на необходимые материалы |
| skills/saitodel/references/ | Пять текущих документов и предлагаемый orchestration.md |
| skills/saitodel/agents/openai.yaml | Текущие метаданные навыка; не конфигурация запуска агентов |
| skills/saitodel/assets/icon.svg | Существующая иконка |
| skills/saitodel/assets/run-record-template.md | Предлагаемый шаблон брифа, задания, версий и доказательств |
| .codex-plugin/plugin.json | Только если совместимость с фактическим клиентом требует этого файла |

Точный manifest готовится по актуальному формату и существующему пакету; здесь схема JSON не задаётся.
Перед выпуском сверяются пути, ссылки, версия, состав и хеши исходных файлов.
Ранее существующие файлы плагина не удаляются только потому, что их нет в этой таблице.
На одной поверхности выбирается один источник обнаружения навыка: standalone либо plugin.
Удаление или отключение прежней установки требует отдельного поручения пользователя, её идентификации и проверки новой поставки; сама проверка не разрешает удаление или отключение.
Пустой поиск не даёт основания создавать второй плагин.

## 4. Роли, чтение и рабочая запись

| Роль | Получает | Делает | Возвращает |
| --- | --- | --- | --- |
| Координатор | Запрос, действующий бриф, решения, состояние проекта | Выбирает режим, критерии и владельцев файлов; управляет бюджетом | Проверенный статус, остаток, следующий шаг |
| Исполнитель | Ограниченное задание, источники, разрешённые файлы | Создаёт результат и устраняет подтверждённые дефекты | Артефакт, точную версию, изменения и технические свидетельства |
| Проверяющий | Исходные требования, критерии, фиксированную версию | Самостоятельно проверяет соответствие и воспроизводит сценарии | Дефекты P0–P2, доказательства и решение по каждому критерию |

Координатор читает SKILL.md и регламент для существенной работы, затем только нужные references.
Исполнитель получает материалы своей задачи; проверяющий — требования и результат напрямую, без подсказки желаемого вердикта.
Для первой приёмки предпочтителен отдельный контекст проверяющего, когда среда поддерживает его создание.
Специалист занимает свободное место в пределах бюджета; вложенные команды не являются стандартным шагом.
Координатор записывает идентификатор каждой реально запущенной роли. Текстовое назначение роли не доказывает запуск.

Одна запись в существующей документации проекта содержит:

1. Цель, режим, аудиторию, CTA, факты, материалы, концепцию, стек и ограничения.
2. Исходные версии и критерии с идентификаторами; решения пользователя и открытые вопросы.
3. Владельцев файлов, задания, результаты и счётчик циклов исправлений.
4. Версии проверенных артефактов, доказательства, статусы и непроверенные пункты.
5. Следующий шаг и данные для продолжения в новой сессии.

Новая сессия восстанавливает эту запись и актуальные источники; наличие шаблона не гарантирует автоматическую память.
Бриф и журнал не содержат секретов. Разрешения инструментов остаются разрешениями среды.

## 5. Приёмка и остановка

Перед реализацией фиксируются обязательные и дополнительные критерии.
Первичная проверка выполняется на определённой версии; исправления получают новые версии.
Повторяются затронутые проверки и существенные проверки регрессии. Уже достаточные доказательства не дублируются без причины.
Бюджет относится ко всей задаче пилота: смена агента или версии не обнуляет число циклов.

| Состояние записи | Условие |
| --- | --- |
| READY | Достаточны исходные данные и разрешён объём работы |
| IMPLEMENTING | Исполнитель создаёт согласованный результат |
| REVIEWING | Отдельный агент проверяет зафиксированную версию |
| FIXING_1 / FIXING_2 | Устраняются подтверждённые дефекты в пределах бюджета |
| ACCEPTED | Все обязательные критерии выполнены и подтверждены |
| BLOCKED | Обязательный критерий не выполнен после бюджета либо необходимое действие недоступно |

Это предлагаемая форма учёта, а не реализованный программный автомат.
Недоступный браузер оставляет визуальную или сценарную проверку невыполненной.
При недоступном делегировании разрешённая работа продолжается последовательно; независимая приёмка остаётся неподтверждённой.
Если независимость обязательна для приёмки, итог этой части — BLOCKED.
Аудит и мастер-промпт не требуют публикации. Статус «неприменимо» требует причины и не считается успешной проверкой.

Для сайта отдельно фиксируются «собрано», «визуально проверено», «сценарии проверены», «опубликовано».
Для самого плагина отдельно фиксируются сохранение source, обнаружение навыка, установка/обновление и выполнение сценария в каждой среде.

## 8. Установка, проверка в средах и откат

По проверкам текущей сессии установка остаётся заблокированной: запись в стандартный каталог не удалась, резервное клонирование остановилось на разрешении адреса сервиса.
Поиск плагина пуст; в списке личных плагинов найден только «Словодел»; полный список cloud skills и локальный поиск не показали «Сайтодел».
Это описывает область выполненного поиска и не доказывает отсутствие плагина во всех средах пользователя.
Повторять эти попытки имеет смысл после конкретного изменения доступа, подключения или среды.

| Этап | Необходимое доказательство |
| --- | --- |
| Идентичность | Точный ID, владелец, scope и текущая версия существующего плагина либо установленный путь навыка |
| Обновление | Успешный штатный механизм и обратное чтение; для плагина — прежний ID и новый release ID |
| Обнаружение Work | Навык виден в соответствующей поверхности и читается после обновления |
| Обнаружение Codex | Навык обнаружен целевым клиентом; зафиксированы клиент и версия |
| Выполнение | Будущий пробный запуск: синтетический бриф сайта и локальный макет с заранее зафиксированными координатором дефектами и ожидаемыми статусами. Проверяющий получает исходный бриф и макет без подсказки дефектов или вердикта; фиксируются фактический запуск ролей и результат. Сейчас этот тест не выполнен |
| Границы | Отсутствие браузера или отдельного агента отражается как ограничение, а не успешный тест |

Перед изменением сохраняются текущая версия, исходники и сведения об установке.
Обновление существующего плагина сохраняет идентичность, аудиторию, подключения и права.
При конфликте релиза сначала читается новая версия; поверх неё не отправляется устаревший пакет.
Откат source выполняется обратным коммитом после проверки последующих изменений, без force push.
Откат пакета — прежнее содержимое через поддерживаемое обновление существующего плагина с допустимой новой версией; затем повторяется проверка обнаружения.
Невозможность восстановления фиксируется отдельным блокером; наличие архива не доказывает работающий откат.

## 9. Условия пилота Натальи

Пилот ещё не выполнен. В этом проекте не зафиксированы актуальный код и URL сайта, бриф, материалы, точное назначение CTA и критерии конкретной страницы.
Их следует восстановить из действующего проекта; данные из памяти не заменяют проверенные исходники.
До сравнительного запуска должны быть выполнены условия:

1. Установлены источник сайта, разрешённая тестовая среда и защищённая текущая версия.
2. Зафиксированы бриф, концепция, тексты, материалы, CTA, устройства, обязательные сценарии и критерии.
3. Выбраны точные baseline и candidate навыка и одинаковый исходный сайт; исторический commit 0b1199a923e9f2af66b05bd38998428d98a4977c не выбирается автоматически.
4. Определён предмет сравнения: изменение процесса или упаковки. Одинаковый текст в новой упаковке сам по себе не доказывает улучшение дизайна.
5. До стартов установлен одинаковый общий бюджет каждого запуска, включая координатора, исполнителей, проверку и исправления.
6. При доступном учёте задаётся общий предел токенов; иначе заранее выбирается одинаковый измеримый лимит времени и отмечается, что равенство токенов не подтверждено.
7. Одинаковы модель/effort, инструменты, исходные данные, критерии и максимум два цикла исправлений; варианты выполняются в отдельных копиях без взаимного переноса результатов.

Сравниваются дизайн, мобильный вид, понятность предложения, CTA, доступность, дефекты, исправления, время и доступный расход.
Пятисекундный тест с человеком и оценка ИИ записываются отдельно. Недоступные метрики не заменяются нулями.
Один сравнительный запуск даёт основание для следующего решения, но не доказывает универсальное превосходство плагина.
